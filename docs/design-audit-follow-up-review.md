# Independent review: filter builder and query history follow-up

**Result: changes requested for two Reset paths.** This is a bounded review of the current follow-up diff against `05dfe16`, not a new score or a reassessment of the earlier completed audit. The tests use mocked frontend database and update bindings; no real database was accessed. The second finding is pre-existing, but falls within the requested unsaved-guard and Reset interaction review.

## Findings

1. **Medium — a failed Reset to an unfiltered query removes the recovery builder.** Apply a filter successfully, open Filters, and choose Reset while a mocked unfiltered table read fails. The workspace displays the error but no Filters button or editable conditions. The workspace Refresh control remains available, but a user cannot choose a filter that worked previously while the unfiltered read continues to fail. In [App.tsx](../frontend/src/App.tsx), the recovery branch at line 1092 requires a nonempty filter or sort, even though `applyTableQuery` recorded recovery columns before submitting Reset. Removing the last condition and applying an empty query follows the same branch. Preserve builder recovery for a failed builder-submitted empty query as well, including an unchanged retry, without mixing columns across tabs. Reproduction: `independent.spec.mjs`, test `observation: failed unfiltered reset removes builder despite prior successful filter`; screenshot `reset-read-failure.png`.

2. **Medium — cancelling a guarded Reset leaves a misleading empty draft.** Apply a filter with value `123`, edit a grid cell, open Filters and choose Reset. In the unsaved-changes dialog choose Keep editing. The grid draft and applied filter survive, but the open builder says “Add a condition to filter rows” while its button still says `Filters · 1`; the prior condition and value are gone from the draft. Applying that apparently empty builder later would remove the still-active filter. In [TableQueryControls.tsx](../frontend/src/TableQueryControls.tsx), line 28 clears the local draft before the guarded `onApply` has been accepted. This ordering was already present at HEAD; the new empty-state guidance makes the disagreement visible, and the guard/Reset flow is in this pass's scope. Keep the current draft intact when the guarded Reset is cancelled, and cover accepted Reset as well. Reproduction: `independent.spec.mjs`, test `observation: cancelling guarded reset clears draft while applied filter remains`; screenshot `reset-cancel-inconsistent.png`.

Both observation tests deliberately assert the observed behavior to document the defects; their passing status is not an assertion that the product behavior is correct.
